# Linear Cycle Planning Plan

## Architecture

1. Add schedule, cycle, scope-event, and cycle-activity tables plus
   `atlas_actions.cycle_id`.
2. Add transactional RPCs for schedule configuration/generation, action
   assignment/removal, and completion/rollover.
3. Add triggers for action auto-add and append-only scope snapshots.
4. Add `cycles:read` and `cycles:write` scopes, while keeping schedule and
   lifecycle operations owner-only.
5. Add Cycle API aggregation, capacity, success, divergence, and graph points.
6. Add `/cycles` and `/cycles/:id` UI plus Action Detail cycle assignment.

## Data Contracts

- `atlas_cycle_schedules`: revisioned recurring cadence configuration.
- `atlas_cycles`: generated timeboxes and immutable completion snapshot.
- `atlas_cycle_scope_events`: append-only graph points.
- `atlas_cycle_activity_log`: append-only lifecycle evidence.
- `atlas_actions.cycle_id`: live cycle membership.

## Integrity Decisions

- Completed cycle fields are protected by a trigger.
- Reconfiguration archives planned cycles rather than deleting them.
- Completion and rollover occur in one RPC transaction.
- Scope events are generated by database triggers so API and direct approved
  service mutations remain observable.
- Historical snapshot metrics are never recomputed from current action state.

## Test Strategy

- Unit-test metrics, capacity, status/date validation, and success weighting.
- HTTP-test owner-only and scoped routes before database access.
- Component-test portfolio/detail/configuration and accessibility.
- Add pgTAP coverage for schedule generation, assignment, scope events,
  completion snapshot, rollover, and non-deletion.
- Run the full repository and browser verification gates.

## Rollout

- Stage migration and application code only.
- Do not apply migrations, configure production schedules, or deploy without
  explicit approval and readback.
